# RVV FFT register-pressure analysis

This document explains the FFT performance results using both measured cycle
counts and compiler-generated V512D128B disassembly. It separates precision,
memory layout, LMUL, and stage fusion because each changes register pressure
in a different way.

## Scope and terminology

The workload is 64 independent 1,024-point FFTs.

- **Bin-major** stores split-complex data as `[bin][batch]`. Vector lanes span
  the 64 batches. A butterfly broadcasts one scalar twiddle to all lanes.
- **Batch-major** stores data as `[batch][bin]`. Vector lanes span consecutive
  bins of one FFT. The kernel loads a vector of different twiddles.
- **Stage fusion** keeps the output of one radix-2 stage live in registers and
  feeds it directly to the next stage, avoiding an intermediate memory
  store/reload when the register file has enough free groups.
- **Whole-register spill** means compiler-generated `vs*r.v` and `vl*re*.v`
  instructions that save and restore vector register groups through the
  stack. They are not FFT dataflow stores and loads.

All FPGA rows use VLEN=512 bits, D=128 bits, a 50 MHz clock, 10-run averages,
and passed validation with zero mismatches.

## Why LMUL creates pressure

RVV has 32 architectural vector registers. An LMUL=m2 value occupies two
registers, m4 occupies four, and m8 occupies eight. Ignoring masks and
temporary constraints, this leaves at most:

| LMUL | Registers per value | Maximum independent groups |
| ---: | ---: | ---: |
| m2 | 2 | 16 |
| m4 | 4 | 8 |
| m8 | 8 | 4 |

A complex radix-2 butterfly needs odd real/imaginary inputs, two complex
products, even real/imaginary inputs, and upper/lower outputs. Lifetimes can
overlap even when the source has few variable names. Stage fusion extends
those lifetimes across a second stage. Consequently, m8's four available
groups are insufficient for the fused FP32 schedule and the compiler spills.

For Q7, the pressure is not determined by the int8 input type alone. Complex
twiddle multiplication widens through int16 to int32. The `m8 accumulator`
variant therefore consumes m8 groups at the widest live point even though its
input vectors use a smaller effective LMUL.

## Direct disassembly evidence

The analyzed files are:

```text
build/baremetal/fft_batched/V512D128B_nn_rvv_baremetal.elf
build/baremetal/fft_batched_int8/V512D128B_nn_rvv_baremetal.elf
```

They were generated by GCC 15.1.0 with:

```text
-O3 -march=rv64gcv_..._zvl512b -mabi=lp64d
```

The counts below are static instruction occurrences within each named
function. A loop can execute an occurrence many times.

### FP32 radix-2 kernels

| Function | Dynamic vector spill area at VLEN=512 | Whole-register stores | Whole-register reloads | Interpretation |
| --- | ---: | ---: | ---: | --- |
| `fft_butterflies_m2` | 0 | 0 | 0 | Non-fused schedule fits |
| `fft_butterflies_m8` | 0 | 0 | 0 | Non-fused schedule fits despite m8 |
| `fft_butterflies_m2_stage_fused` | 0 | 0 | 0 | Fused values still fit |
| `fft_butterflies_m4_stage_fused` | 256 bytes | 1 × `vs4r.v` | 1 × `vl4re32.v` | Mild pressure |
| `fft_butterflies_m8_stage_fused` | 3,584 bytes | 12 × `vs8r.v` | 16 × `vl8re32.v` | Severe pressure |

The fused-m8 prologue reads `vlenb`, multiplies it by 56, and subtracts that
amount from `sp`. At VLEN=512, `vlenb=64`, so the vector spill area is
`56 × 64 = 3,584` bytes, in addition to the 96-byte scalar frame. The
disassembly then repeatedly saves and restores m8 groups:

```asm
csrr       t0,vlenb
li         t1,56
mul        t1,t1,t0
sub        sp,sp,t1
vs8r.v     v16,(...)
vl8re32.v  v16,(...)
```

The m4 fused function reserves only `4 × vlenb = 256` bytes and contains one
`vs4r.v`/`vl4re32.v` pair. The m2 fused function contains no whole-register
spill instruction.

### Q7 bin-major radix-2 kernels

| Function | Dynamic vector spill area at VLEN=512 | Whole-register stores | Whole-register reloads |
| --- | ---: | ---: | ---: |
| `fft_butterflies_q7_m2` | 0 | 0 | 0 |
| `fft_butterflies_q7_m4` | 0 | 0 | 0 |
| `fft_butterflies_rvv_q7` (m8 accumulator) | 512 bytes | 2 × `vs8r.v` | 2 × `vl8re32.v` |
| `fft_butterflies_q7_m2_stage_fused` | 0 | 0 | 0 |
| `fft_butterflies_q7_m4_stage_fused` | 0 | 0 | 0 |
| `fft_butterflies_q7_m8_stage_fused` | 1,536 bytes | 13 total | 6 total |

The non-fused m8 prologue reserves `8 × vlenb = 512` bytes. Its two m8
stores and two m8 reloads show that Q7 widening is sufficient to spill even
without fusion. The fused-m8 prologue reserves `24 × vlenb = 1,536` bytes.
Its stores comprise seven `vs2r.v`, three `vs4r.v`, and three `vs8r.v`
instructions; its reloads comprise three `vl4re16.v` and three `vl8re32.v`
instructions. The m2 and m4 variants, fused or not, have no dynamic vector
stack allocation and no whole-register spill instruction.

These functions are marked `noinline` so the optimized ELF retains one symbol
per analysis target. Without that boundary, GCC 15 can inline the six
bin-major variants into the benchmark driver, making per-kernel spill counts
ambiguous even though the executed arithmetic is unchanged.

### Q7 batch-major radix-2 kernels

| Function | Dynamic vector spill area at VLEN=512 | Whole-register stores | Whole-register reloads |
| --- | ---: | ---: | ---: |
| `fft_batch_major_q7_m2` | 0 | 0 | 0 |
| `fft_batch_major_q7_m4` | 0 | 0 | 0 |
| `fft_batch_major_q7_m8` | 1,024 bytes | 2 × `vs8r.v` | 2 × `vl8re32.v` |

The m8 batch-major function computes `16 × vlenb` for its dynamic stack area,
which is `16 × 64 = 1,024` bytes at VLEN=512. Its hot region spills two m8
groups before completing the widened int32 calculation. The m2 and m4
functions have only a 64-byte scalar stack frame and no vector whole-register
spill/reload.

The spill is not the only batch-major cost. Its disassembly also contains
vector-vector twiddle operations (`vwmul.vv` for Q7), because adjacent vector
lanes use different twiddles. Bin-major applies one shared twiddle to all 64
batches and uses scalar-vector operations. Therefore layout and register
pressure contribute simultaneously.

### FP32 batch-major: why m2 can win

The FP32 batch-major source makes substantially more vector values live than
the bin-major scalar-twiddle path. One inner iteration names:

```text
xr xi wr wi pr pi ar ai ur lr ui li
```

The compiler can reuse registers after the final use of an input, so these
twelve names are not necessarily live simultaneously. Nevertheless, four
input/twiddle vectors, two products, the even input, and output temporaries
overlap around the complex multiply and butterfly:

| LMUL | Maximum groups | Batch-major scheduling consequence |
| ---: | ---: | --- |
| m2 | 16 | Enough room for inputs, twiddles, products, and outputs with useful overlap |
| m4 | 8 | Borderline; the compiler must shorten live ranges and serialize more loads/operations |
| m8 | 4 | Cannot retain the working set; aggressive serialization or spill/reload is unavoidable |

LGVV512D128 illustrates the capacity cliff:

| FP32 batch-major variant | Bit reversal | Butterfly | Complete FFT | Relative butterfly |
| --- | ---: | ---: | ---: | ---: |
| m2 | 3,995,076 | **7,027,531** | **11,022,607** | 1.00x |
| m4 | 4,523,114 | 7,086,306 | 11,609,420 | 1.008x |
| m8 | 4,015,303 | 16,912,003 | 20,927,306 | 2.406x |

Two qualifications are important:

1. The m2 and m4 butterfly regions differ by only 0.84%. This is a near tie,
   not evidence that m2 has intrinsically higher arithmetic throughput.
   m2 has more scheduling freedom, while m4 executes fewer chunks; those
   effects almost cancel.
2. The bit-reversal implementation does not use the selected butterfly LMUL.
   Its 3,995,076 versus 4,523,114-cycle difference is run-to-run/cache
   variation and must not be presented as an m2 register-pressure benefit.
   The LMUL conclusion should therefore be based on butterfly cycles.

m8 is different: its butterfly region is 2.41x slower, which is far beyond
the m2/m4 measurement spread and is consistent with only four architectural
groups being available for a vector-vector complex multiply. A current FP32
batch-major ELF was not retained in the workspace, so this report does not
claim a specific `vs8r.v` count for that function. The Q7 m8 spill count above
is direct disassembly evidence; the FP32 m8 conclusion is a source-level
register-capacity analysis supported by FPGA cycles.

Across all FP32 configurations, m2 is often the best *complete* batch-major
variant, while m4 can still have the best butterfly counter on some
configurations. The defensible conclusion is therefore:

- m2/m4 is the useful operating region;
- m2 has lower register pressure;
- m4 can recover the difference through a larger VLMAX;
- m8 crosses a clear pressure/utilization cliff.

## Cycle results explained by pressure

### FP32 bin-major FPGA result

| Variant | Butterfly cycles | Relative to its non-fused form | Spill evidence |
| --- | ---: | ---: | --- |
| m2 | 861,070 | baseline | none |
| m2 fused | 842,949 | 1.02x faster | none |
| m4 | 828,128 | baseline | none in the baseline |
| m4 fused | **773,128** | 1.07x faster | one m4 spill/reload pair |
| m8 | 854,032 | baseline | none |
| m8 fused | 5,316,059 | **6.22x slower** | 12 m8 stores, 16 m8 reloads |

This is the clearest register-pressure experiment:

1. Non-fused m2, m4, and m8 are nearly equal because their individual
   butterflies fit without whole-register spilling.
2. Fusion helps m2 and m4 by removing the intermediate stage boundary.
3. Fused m8 crosses the capacity threshold. Spill traffic overwhelms the
   saved FFT memory traffic and makes it more than six times slower.

Spike showed only a 1.23x fused-m8 slowdown. The FPGA shows 6.22x because
spill cost depends on the memory system and vector implementation. Spike is
valid for correctness and instruction comparison, but its cycle model must
not be used as the final FPGA spill-cost estimate.

### Q7 bin-major FPGA result

| Variant | Butterfly cycles | Fusion effect |
| --- | ---: | ---: |
| m2 accumulator | 1,099,285 | baseline |
| m2 accumulator fused | 1,208,405 | 1.10x slower |
| m4 accumulator | **1,036,779** | baseline, fastest |
| m4 accumulator fused | 1,125,477 | 1.09x slower |
| m8 accumulator | 1,225,322 | baseline |
| m8 accumulator fused | 1,446,335 | 1.18x slower |

Q7 requires widening, narrowing, rounding, and saturation in addition to the
complex multiply. Those extra live values make m8 unattractive even without
two-stage fusion. Unlike FP32, fusion does not win at any accumulator LMUL on
this FPGA. The best balance is m4: it reduces loop/chunk overhead without
shrinking the usable register-group count to four.

### Layout ablation and FPGA campaign

Both layouts have Spike ablations and complete FPGA measurements. All nine
FPGA configurations now run bin-major and batch-major kernels in both
precisions. On LGVV512D128, the best Q7 batch-major radix-2 FFT takes
7,918,006 cycles versus 1,074,399 cycles for bin-major, a `7.37x` penalty.
The corresponding FP32 values are 11,022,607 and 926,835 cycles, an `11.89x`
penalty.

| Environment | Precision | Best bin-major FFT cycles | Best batch-major FFT cycles | Batch-major penalty |
| --- | --- | ---: | ---: | ---: |
| FPGA LGVV512D128 | FP32 | 926,835, m4 fused | 11,022,607, m2 | 11.89x |
| FPGA LGVV512D128 | Q7 | 1,074,399, m4 | 7,918,006, m4 | 7.37x |
| Spike VLEN=128 | FP32 | 579,302, m8 | 7,909,267, m4 | 13.65x |
| Spike VLEN=512 | Q7 | 386,632, m4 | 4,919,856, m8 | 12.72x |

Batch-major loses for three separable reasons:

1. Bit reversal is repeated independently for every batch rather than swapping
   one contiguous 64-batch row.
2. Twiddles become vectors instead of one scalar broadcast across batches.
3. Larger LMUL increases live-group pressure; Q7 batch-major m8 demonstrably
   spills, while FP32 m8 shows a large cycle cliff. FP32 m2 and m4 remain
   close in butterfly cycles, with m2 often winning the complete FFT.

Each row compares layouts within one environment and precision, not FP32
against Q7. The Q7 Spike result selecting m8 does not contradict the FPGA
spill evidence:
instruction/chunk reduction can outweigh a small simulated spill penalty.
The FP32 FPGA fused-m8 result shows why the same choice can become disastrous
when real spill traffic reaches the memory system.

## Register-pressure conclusion

LMUL should not be selected only by maximum vector width. For this FFT:

- Use bin-major to expose the independent batch dimension and broadcast one
  twiddle scalar.
- Use m4 as the conservative hardware choice when widening or fusion extends
  value lifetimes.
- Use m8 only when disassembly confirms that the complete hot kernel has no
  `vs8r.v`/`vl8re*.v` spill pair.
- Treat stage fusion as profitable only while its intermediate complex values
  remain in the vector register file.
- Report disassembly together with cycles: LMUL alone does not reveal whether
  the compiler spilled, and Spike alone does not reveal the FPGA spill cost.

## Reproducing the disassembly check

```sh
OBJDUMP=/opt/riscv_baremetal_medany/bin/riscv64-unknown-elf-objdump

$OBJDUMP -d \
  --disassemble=fft_butterflies_m8_stage_fused \
  build/baremetal/fft_batched/V512D128B_nn_rvv_baremetal.elf

$OBJDUMP -d \
  --disassemble=fft_batch_major_q7_m8 \
  build/baremetal/fft_batched_int8/V512D128B_nn_rvv_baremetal.elf

$OBJDUMP -d \
  --disassemble=fft_butterflies_q7_m8_stage_fused \
  build/baremetal/fft_batched_int8/V512D128B_nn_rvv_baremetal.elf
```

Search the output for:

```text
vs2r.v  vs4r.v  vs8r.v
vl2re*.v  vl4re*.v  vl8re*.v
```
